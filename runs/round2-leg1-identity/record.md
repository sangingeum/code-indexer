# Record — symbol identity and parse verdicts

Round 2, leg 1. Governed by ADR-0002 sections 1-3, ADR-0001 section 2, ADR-0004
section 7's parse-verdict rule, and the round-2 entry of the overhaul plan.
This file is the authored record; it is written first and kept current, so a
budget stop loses nothing that was already decided.

## What this leg lands

1. Manifest schema revision 7: identity model, reference target columns,
   `chunks` table, per-file parse verdict.
2. Parse verdicts from the parser's own result, and `index-status` counts.
3. Refusal on every row-reading surface for a `needs-reindex` project.
4. Extraction-version bump and its consequence for every registered project.

Steps are recorded below as they land; open items are named rather than
implied.

## Schema (revision 7)

One revision covers the whole round: the identity model, the staged reference
target columns, the chunk table and the per-file parse verdict land together,
so the next leg populates what this one created and adds no DDL.

`symbols` (re-created, not altered):

    id INTEGER NOT NULL UNIQUE          -- revision-scoped surrogate
    file TEXT NOT NULL
    qualified_name TEXT NOT NULL        -- container chain + name: Core.search
    container TEXT                      -- parent qualified name, NULL at top
    language TEXT                       -- copied from files.language
    symbol_type TEXT NOT NULL           -- the kind column, name unchanged
    decl_hash TEXT NOT NULL             -- sha256 of the normalized signature
    name TEXT NOT NULL                  -- the leaf name, unchanged
    start_line INTEGER NOT NULL         -- attribute, not identity
    end_line INTEGER NOT NULL           -- attribute, not identity
    source TEXT NOT NULL DEFAULT 'regex'
    signature TEXT
    visibility TEXT
    PRIMARY KEY (file, qualified_name, symbol_type, decl_hash)

Indexes: `idx_symbols_id` (unique, for the future join from `refs`),
`idx_symbols_name`, `idx_symbols_qualified`, `idx_symbols_container`,
`idx_symbols_file_start`. The kind column keeps its name `symbol_type` — the
record's reason stands: renaming it touches fourteen JSON consumers and buys no
query.

`decl_hash` is `sha256:` + sha256 of the whitespace-collapsed signature the
chunker already produces (`chunker.declaration_hash`). Where a row carries no
signature the declaration's observed first line is the basis, and a row with
neither (only hand-written rows) is hashed on its observed range so two such
rows never collapse. Consequence, stated rather than papered over: **a reformat
that changes the signature changes the identity.**

The surrogate `id` is assigned at insert from the manifest's own counter
(`meta.symbol_id_seq`), inside the same transaction as the row write, so it is
unique within a revision and never reused after a delete. It is regenerated by
any reparse and meaningless across revisions; JSON reports it as `symbol_id`
beside `index_revision`. It is not the edit-plan locator (ADR-0002 section 2).

`refs` gains `target_symbol_id INTEGER` and `resolution TEXT`, both nullable,
both left NULL by this leg — population is a later leg.

`files` gains `parse_verdict TEXT`.

`meta` needs no new columns: it is key/value, and the three version axes are
keys (`extraction_version`, `embedding_version` to be written by leg 2,
`schema_version`). Nothing is created for them here beyond the existing table.

`chunks` is created and left empty:

    chunks(file, chunk_index, start_line, end_line, symbol, symbol_type,
           chunk_hash, text)   PRIMARY KEY (file, chunk_index)

## Migration

Runs on open, inside one transaction, and every statement is
`IF NOT EXISTS`/`PRAGMA`-guarded, so it is idempotent and an already-revision-7
manifest is left untouched.

- `symbols`: if the table exists and carries no `decl_hash`, it is dropped and
  re-created. The old key `(file, name, start_line)` is line-bearing and the
  new columns cannot be derived from it — `qualified_name` needs the container
  chain the old extractor never stored, and `decl_hash` needs a signature a
  legacy row may not carry. Replacing the rows empty is the honest option;
  fabricating a hash would be a lie about identity. No read answers from the
  empty table, because the same round's extraction-version bump makes every
  project `needs-reindex` and every row-reading surface refuses (below).
- `files`: `mtime_ns`, `inode`, `loc`, `language`, `parse_verdict` added when
  missing.
- `refs`: `receiver`, `target_symbol_id`, `resolution` added when missing.
  The retired `symbol_refs` table is dropped.
- `chunks` and `index_errors` created when missing.
- `schema_version` is raised to 7 only upward, never back.

`executescript()` was replaced by a statement loop: `executescript` commits the
surrounding transaction, which would have made the migration non-atomic.

**A manifest already at 7 between the two legs.** Nothing changes: the DDL for
revision 7 is complete on this landing, leg 2 only writes rows into `chunks`,
the `meta` version keys and the two `refs` columns. The migration is guarded by
column inspection, not by the version number alone, so reopening a 7 manifest
runs no DDL and rewrites no row; the revision number never has to move again
for this round. That is the whole point of paying for the schema once.

Migration test: `tests/test_identity.py` builds a hand-written version-6
manifest (one old-key row), opens it, and asserts schema 7 with zero rows
carried and both staged columns NULL. It then runs a real pass on a throwaway
root: one loose v6 row becomes three identified rows (two top-level, one
nested with container `Core`), every one carrying a `decl_hash`.

## Qualified names

`container` is the qualified name of the enclosing declaration and
`qualified_name` is that chain joined to the leaf: a method inside `Core` is
`Core.search` with `container = "Core"`; a top-level declaration is its bare
name with `container = NULL`. The chain is threaded through the AST walk
(`ts_chunker._walk`), so nesting is decided by the parse, not by re-splitting a
name string. Regex-fallback chunks have no container (the fallback has no tree).

One consequence worth naming: a declaration the chunker observes twice (a
decorated definition larger than the split cap is emitted as an outer and an
inner unit) now has the same qualified name, kind and declaration hash, so it
is ONE row with the first observed range. Two byte-identical declarations in
one file are likewise one symbol; two declarations that differ only by their
signature stay two rows (the overload case).

## Extraction-version bump

`EXTRACTION_VERSION` 4 -> 5. The reason is a fact, not a convenience: a
`decl_hash` cannot be derived from rows written by the old extractor (it never
stored a container chain, and its rows may carry no signature), and the parse
verdict did not exist. There is no way to backfill either from the stored rows.

What that means for every registered project, without exception: its recorded
fingerprint no longer matches this build, so `index-status` reports
`fingerprint=needs-reindex`, and every row-reading surface refuses with exit 4
until its ordinary pass runs. The pass is `reindex-project` (or any pass the
watcher runs under the new code); it is not a paid operation and it does not
rebuild the vector collection, because the embedding identity does not change.
No live project was reindexed by this leg: that operational step belongs to the
round's gate and to the owner, not to a development leg's side effect.

`CHUNKER_VERSION` is unchanged: chunk boundaries, unit types and split rules did
not move, so vectors stay valid and the pass re-embeds from the content-addressed
cache rather than from the model.

## Parse verdicts

Source: the parser's own result, never the chunker. `ts_chunker.parse_file`
runs ONE parse and returns `(chunks, verdict)`:

- `parse_error` when `root.has_error` is set or the tree contains a missing
  node (`is_missing`); the tree is still walked and its chunks are kept.
- `parsed` otherwise.
- `parse_unavailable` whenever the function cannot stand behind an AST — no
  grammar pack, no grammar for the extension, a parser exception, or an AST
  walk that produced no chunks. Every one of those paths takes the regex
  fallback, so "the regex chunker handled this file" and "parse_unavailable"
  are the same statement.

How it differs from the chunker's own behaviour, which is why it cannot be
inferred: the chunker never fails. It falls back on a missing grammar, on a
parser exception and on zero chunks, and it happily walks an error-tolerant
tree. A file with a syntax error therefore returns a full chunk list, and a
chunker-derived verdict would call it `parsed`; a declaration-free file that
took the fallback would also read as `parsed`. Both cases are pinned in
`tests/test_parse_verdict.py`.

Shape: a per-file column, `files.parse_verdict` (one of the three values, NULL
only on rows written before revision 7). A column rather than a side table
because the verdict is a property of the file row the pass already writes, and
because `index-status` needs one `GROUP BY` rather than a join.

`index-status` reports all three counts per project, always all three keys:

- text: `parse=parsed:3,parse_error:1,parse_unavailable:2`
- JSON: `"parsed": 3, "parse_error": 1, "parse_unavailable": 2` alongside
  `schema: 1` (additive; the schema number does not move).

`index-status` stays answerable on a `needs-reindex` project by contract: it
reports the counts the rows carry, including when those rows are about to be
replaced.

## Refusal matrix

Binding rule: a surface that answers from stored rows refuses a
`needs-reindex` project — exit 4, EMPTY stdout, exactly one
`RebuildRequiredError:` line on stderr naming the remedy. Exit codes below are
the ones the suite observed, per surface, in text mode and in the surface's own
machine-readable mode (`tests/test_refusal_needs_reindex.py` runs both).

| surface | argv used by the test | machine-readable spelling | observed |
|---|---|---|---|
| `find-symbol` | `find-symbol Core` | `--json` | 4 / 4, stdout empty |
| `find-definition` | `find-definition Core` | `--json` | 4 / 4, stdout empty |
| `outline` | `outline a.py` | `--json` | 4 / 4, stdout empty |
| `skeleton` | `skeleton` | `--json` | 4 / 4, stdout empty |
| `get-code-context` | `get-code-context a.py --start-line 1 --end-line 2` | `--json` | 4 / 4, stdout empty |
| `find-references` | `find-references Core` | `--json` | 4 / 4, stdout empty |
| `find-callers` | `find-callers main` | `--json` | 4 / 4, stdout empty |
| `find-callees` | `find-callees main` | `--json` | 4 / 4, stdout empty |
| `deps` | `deps a.py` | `--format json` (NOT `--json`) | 4 / 4, stdout empty |
| `changed-symbols` | `changed-symbols` | `--json` | 4 / 4, stdout empty |
| `overview` | `overview` | `--json` | 4 / 4, stdout empty |
| `list-projects` | — | `--json` | 0, still answers |
| `lookup-project` | `<path>` | — | 0, still answers |
| `index-status` | `<path>` | `--json` | 0, still answers |
| `doctor` | — | `--json` | never 4; reports its checks |

Three notes the matrix cannot carry:

- `deps` has **no** `--json` flag: ADR-0003 section 7 grants `--json` to five
  read commands and `deps` is not one of them; its JSON mode is
  `--format json`. The test uses each command's real spelling (read from
  `--help`), and adding `--json` to `deps` would be an unratified surface
  change.
- `overview` is refused here although the brief's enumerated list stops at
  ten surfaces: the review's finding named `find-symbol`/`overview` as the
  defect, and `overview` reads manifest rows like the rest.
- `--refresh` on a refusing surface runs the pass FIRST and then asserts, so
  one refresh repairs the project and the command answers normally
  (`tests/test_refusal_needs_reindex.py` pins that too).

The former stderr warning on these surfaces is gone (`_warn_rows_staleness`
removed). A caveat printed above an answer still reads as a fact about the
code; the honest shape is a refusal. `Core.rows_staleness` remains as a
diagnostic primitive and is still exercised by
`tests/test_staleness_reporting.py`.

## Not done, honestly

- `changed-symbols` is refused before it touches git, so its refusal is tested
  on a non-git throwaway project; the git-repo precondition itself is covered

  anyway).
