                                                                                
 Usage: code-indexer [OPTIONS] COMMAND [ARGS]...                                
                                                                                
 Code intelligence for agents: index a repository into SQLite and answer        
 structural, lexical and optional semantic queries (one-shot CLI; no daemon).

│ find-callers             Who references this symbol: fan-in BFS over the     │
│                          single reference store                              │
│                          (tree-sitter `call`/`type`/`base_class`/`member`    │
│                          rows, confidence `ast`,                             │
│                          for                                                 │
│                          python/typescript/tsx/javascript/c/cpp/go/csharp,   │
│                          plus the textual                                    │
│                          `identifier` / `includes` rows, confidence          │
│                          `heuristic`, for every other                        │
│                          language, where comments and strings DO match) and  │
│                          import-based edges.                                 │
│                          The graph is TEXTUAL AND UNBOUND by design: names   │
│                          are matched as text,                                │
│                          there is no compiler resolution, so a heuristic row │
│                          is a navigation aid,                                │
│                          not a resolved call. NAME may be dotted             │
│                          (`Type.Member`): the qualifier                      │
│                          resolves against the symbol rows and the fan-in is  │
│                          matched on the                                      │
│                          trailing member name; the subject is reported once  │
│                          on the `note:` lines,                               │
│                          and a direct hit carries `receiver=<expr>` only     │
│                          when the store actually                             │
│                          holds a receiver for that row (a member access      │
│                          records the receiver                                │
│                          expression as written) — transitive nodes never     │
│                          carry one. When the name                            │
│                          has no definition row (symbols cover                │
│                          method|class|function|enum|interface|struct;        │
│                          properties and fields are not                       │
│                          extracted), the search seeds from the reference     │
│                          rows and says so on                                 │
│                          `note:` lines instead of printing a bare `no        │
│                          results`. Every CALL SITE is                        │
│                          its own node (two calls to the same target inside   │
│                          one function are two                                │
│                          hits, each with its own line and receiver), and an  │
│                          answer the depth or                                 │
│                          node cap left incomplete says so: the JSON payload  │
│                          carries `truncated`                                 │
│                          and `omitted` beside `roots`, and the tree gains a  │
│                          `note:` line naming                                 │
│                          the cap. The answer is honest about the NAME too:   │
│                          JSON carries                                        │
│                          `match_count` and, when the subject has more than   │
│                          one definition, an                                  │
│                          `ambiguity` block listing every candidate the walk  │
│                          unions over; each                                   │
│                          direct hit then carries `targets`, the candidate    │
│                          definition(s) it can                                │
│                          belong to. Text mode prints the tree plus one line  │
│                          saying the name                                     │
│                          resolved to se<qa-profile>l definitions. For every          │
│                          reference TO a name use                             │
│                          `find-references`.                                  │
│ find-callees             What this symbol references: fan-out BFS over the   │
│                          `refs` table                                        │
│                          (same store and confidence rules as `find-callers`; │
│                          the graph is textual                                │
│                          and unbound by design). A callee is identified by   │
│                          its TARGET, not by the                              │
│                          call site — this walk answers "what does this       │
│                          symbol reach", so one target                        │
│                          reached twice is one callee. The opposite of        │
│                          `find-callers`, deliberately.                       │
│                          An answer the depth or node cap left incomplete     │
│                          reports `truncated` /                               │
│                          `omitted` in JSON and a `note:` line in the tree.   │
│                          The subject NAME is                                 │
│                          reported too: JSON carries `match_count` and, when  │
│                          the name has se<qa-profile>l                                │
│                          definitions, an `ambiguity` block, with `targets`   │
│                          on each direct callee                               │
│                          naming the definition it was reached from. Text     │
│                          mode prints the tree plus                           │
│                          one line saying the name resolved to se<qa-profile>l        │
│                          definitions. For references                         │
│                          TO a symbol across both stores use                  │
│                          `find-references`.                                  │
│ deps                     Import graph around one file (resolved edges only). │
│                          The payload keeps                                   │
│                          its per-level `in` / `out` dicts and gains          │
│                          `truncated` and `omitted`; a                        │
│                          result the depth or node cap left incomplete also   │
│                          prints a `note:` line                               │
│                          naming the cap.                                     │

│                          index (no semantic                                  │
│                          search). Exact AST-first, capped substring          │

│ find-definition          Find where a symbol is declared (exact name match   │
│                          only). A read:                                      │
│                          --refresh is the only flag that makes it write,     │

│                          the JSON object carries the staleness block.        │
│ get-code-context         Retrieve ONLY the relevant source lines instead of  │
│                          whole files.                                        │
│ find-references          Find references TO a symbol in the single reference │
│                          store. Every row                                    │
│                          carries the relationship it was extracted with and  │
│                          its confidence, so a                                │
│                          heuristic `identifier` hit is never mistaken for a  │
│                          resolved call:                                      │
│                          tree-sitter rows                                    │
│                          (`call`/`type`/`base_class`/`member`/`includes`,    │
│                          confidence `ast`) for                               │
│                          python/typescript/tsx/javascript/c/cpp/go/csharp —  │
│                          `member` is a member access read such as a C#       │
│                          property/field, `includes`                          │
│                          is the import/include target, and `member`/`call`   │
│                          rows record the receiver                            │
│                          expression as written when it is a plain identifier │
│                          — plus a textual scan                               │
│                          (confidence `heuristic`) for every other language:  │
│                          an identifier followed                              │
│                          IMMEDIATELY by `(` is a `call`, any other           │
│                          identifier is an `identifier`,                      │
│                          and an import/include line is an `includes`.        │
│                          Comment-leading lines                               │
│                          (`#`, `//`, `*`, `--`) are skipped there, but       │
│                          trailing comments and                               │
│                          strings DO match. A filtered report that comes back │
│                          empty never reads as                                │
│                          "the name is absent": when rows exist under another │
│                          relationship, the line                              │
│                          names the unfiltered count and the relationships    │
│                          that do carry it (one                               │
│                          aggregate query, not a second report). A bare `no   │
│                          references to X` is                                 │
│                          printed only when the store has none at all.        │
