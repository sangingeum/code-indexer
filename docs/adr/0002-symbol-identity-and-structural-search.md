# ADR-0002: symbol identity and structural search

- Status: proposed (awaiting owner ratification)
- Date: 2026-11-07
- Deciders: owner (ratification), architecture review
- Supersedes / Superseded by: --

## Decision in one paragraph

A symbol row is identified by `(file, qualified name, kind, declaration hash)` with start and end line demoted to attributes, so a one-line shift no longer changes the identity; the row gains a surrogate `id` that is an index-internal join key, regenerated by a reindex and never a cross-process contract or part of an edit plan. A reference keeps the name it observed as evidence and gains a nullable resolved target in the same schema step, populated only where resolution is unique and never for textual identifier rows. Structural search extends `find-symbol` with filters rather than adding a second query surface, and every ambiguous lookup returns candidates with disambiguating metadata, never a silent pick.

## Context

1. There is no stable symbol identity. The primary key is `(file, name, start_line)` (`src/code_indexer/manifest.py:62`), and the row carries no surrogate id, no qualified name, no parent, no language and no version (audit section 3). `end_line` is not in the key, so two rows cannot differ only by end line; a definition moved down one line is a different key.
2. Ambiguity is common, and line numbers are the only thing that currently resolves it. On the live index: 1,733 symbol rows over 1,104 distinct names; 141 names carry more than one row, covering 770 rows (44% of all symbol rows); and 83 `(file, name)` groups hold more than one row inside the same file -- the overload and re-declaration cases that only `start_line` separates (artifact `runs/milestone0/probe-symbol-identity.txt`).
3. A reference carries no target. `refs.to_name` is a bare string with `relationship`, `confidence` and `receiver` (`src/code_indexer/manifest.py:71-82`); graph walks match on the trailing member name after splitting on the last dot (`src/code_indexer/graph.py:188-204`, `:225`), so two `run()` methods are indistinguishable and fan-in is a union by accident rather than by decision (audit section 3, section 8).
4. Attribution exists only where an AST parser wrote the row. Of 113,751 reference rows, 9,307 (8.2%) carry an enclosing symbol, and every attributed row is AST-sourced: `call/ast` 7,575 of 8,698, `type/ast` 1,584 of 1,600, `base_class` 15 of 15. The 101,197 `identifier/heuristic` rows carry none (artifact `runs/milestone0/probe-ref-attribution.txt`, produced by `runs/milestone0/probe_ref_attribution.py`).
5. A structural query built before an identity is a query rewritten afterwards. Kind, file and substring filters already live on `find-symbol` (`src/code_indexer/cli.py:1406-1425`), inheritance and call rows are already stored, and six other surfaces render symbol rows -- so the missing ingredient is identity, not storage (audit section 10, item 3; section 11, questions 1 and 9).

## Decision

### 1. The identity model

| Column | Meaning | In the key |
|---|---|---|
| `file` | repository-relative path | yes |
| `qualified_name` | container chain joined to the name, e.g. `Core.search` | yes |
| `symbol_type` | the kind column, its name unchanged | yes |
| `decl_hash` | sha256 of the normalized signature the chunker already produces | yes |
| `container` | parent qualified name, or NULL at top level | no, denormalized for filtering |
| `language` | copied from `files.language` | no, denormalized for filtering |
| `id` | single-column surrogate, assigned at insert | no |
| `start_line`, `end_line` | ranges as observed | no |
| `signature`, `visibility`, `source` | as today | no |

The key is line-free, so a line shift preserves identity. A reformat that changes the signature changes `decl_hash` and therefore the identity -- that is stated, not papered over, and matches the proposal's own rule "do not promise stability across arbitrary source transformations". Where a row carries no signature (the column tolerates NULL for legacy rows, though the live index has none: 1,589 AST-sourced and 144 regex-sourced rows, all with a signature), `decl_hash` hashes the declaration's observed first line with whitespace normalized, so the key is total for every row.

The column stays named `symbol_type`: renaming it to `kind` would touch fourteen JSON consumers for no query benefit.

### 2. The surrogate id is revision-scoped

- `symbols.id` exists to join `refs` to `symbols` without string matching. It is regenerated by any reparse and is meaningless across index revisions.
- It is exposed in JSON as `symbol_id` next to `index_revision`, and a consumer that persists it across a reindex is wrong by contract.
- It is **not** the edit-plan locator. Requirement 2's locator is `(path, language, qualified name, kind, decl_hash)` plus file-level preconditions -- exactly the key above plus the file hash, so this model supplies the plan without pretending the id is durable.

### 3. Reference targets are added but staged

- `refs` keeps `to_name`, `relationship`, `confidence`, `receiver` and `from_symbol` unchanged. It gains two nullable columns in the same migration: `target_symbol_id` and `resolution` (`none|same_file|same_project|backend`).
- Population is deferred to a later leg; the column is paid for now so that identity lands as one schema change rather than two.
- Population rule: a target is written only when exactly one definition matches within the resolution scope. `identifier/heuristic` rows are never resolved: a textual occurrence of a name is not evidence about which definition it means, and inventing a target would convert a heuristic into a claim.
- Graph commands read resolved targets first and fall back to the trailing-name match that exists today. No answer can regress, because an unresolved edge behaves exactly as it does now, and every hit names the resolution it used.

### 4. Structural search extends `find-symbol`

`find-symbol` already carries kind, file, substring and limit filters, and it is the surface six other commands render through. A second query command would duplicate those filters and split the JSON contract. The minimum filter set worth shipping, and what answers each:

- `--kind` (today's `--type`/`--symbol-type`, kept as aliases) -- the `symbol_type` column.
- `--name-pattern` (glob) -- `idx_symbols_name` turns `*Manager` into a range or LIKE scan; no new index needed.
- `--container` -- the new column, which is why it is denormalized.
- `--visibility` -- the existing column.
- `--language` -- the new denormalized column; a join through `files` would also work, and the copy avoids one on every query.
- `--inherits NAME` -- `refs.relationship='base_class'` joined on `from_symbol`.
- `--has-call NAME` -- `refs.relationship='call'` joined on `from_symbol`.

`--inherits` and `--has-call` answer from attributed syntax only, so every candidate carries `evidence: ast|heuristic|unknown`. A symbol in a file with no AST extractor reports `unknown`, never "no", because 91.8% of reference rows prove that absence of an attributed call is not absence of a call.

### 5. Ambiguity is reported, never resolved silently

- JSON carries `match_count`, and when it exceeds one, `ambiguity.candidates[]` with file, range, kind, container, signature, language and `decl_hash` for each.
- A command that must act on one symbol and cannot disambiguate refuses with `ArgumentError` and lists the candidates. None of the shipped structural filters needs to pick.
- `find-callers` and `find-callees` union over every candidate and label each hit's target instead of taking the first row.

## Requirements this record resolves

- **Requirement 2** in full. Its locator is the key in section 1 plus the file hash; its refusal of a permanent global id is honoured by section 2; its honesty requirement ("say which of the two it verified, structural or semantic") is satisfiable because the locator is structural by construction and a later language-server leg can add a semantic identifier as an extra field without changing this key.
- **Disagreement with the proposal's identity list:** proposal section 5.2 puts "parser/index version" inside the identity. Rejected. A parser version is a property of the pass that wrote every row, already recorded once in `meta`; a per-row copy is data that must be re-stamped on every reparse and would make rows from one pass look heterogeneous. A version in the key also makes `decl_hash` redundant, which is the part that actually carries stability.
- **Disagreement with the audit's framing of structural search as half-cheap** (audit section 10, item 3): the stored call and inheritance rows answer for AST-parsed files only, and `--has-call` can be answered for 87% of AST call rows and none of the textual ones. The filter is worth shipping with an explicit `unknown`, but it is a syntax-evidence filter, not a complete one.
- Requirements 3 and 4 belong to the successor record set and ADR-0003 respectively; nothing is dropped.

## Alternatives considered, and why rejected

- **A content hash of the whole declaration as the primary identity.** Attractive for stability, but any body edit changes it, so `find-definition` would report the same symbol as a different symbol exactly when a user is looking at a change. The signature hash is the stable half and the body is what edits touch.
- **A permanent global id assigned once and never changed.** Requires a durable identity store outside the manifest, and a reindex cannot rebuild ids for symbols whose text changed -- precisely the cases an edit plan must revalidate. It also contradicts requirement 2.
- **Resolve every reference during the identity change.** Correct in the end, but it needs the import graph and a scope model, and it would double the first reindex's cost while the identity key is still settling. Staged, with the column paid for now.
- **A new `symbols` / `search-ast` command.** Duplicates six filters that already exist, splits the JSON contract, and gives agents two answers to the same question.
- **Keep the trailing-name match and fix ambiguity with a tie-breaker (file match, then definition-over-reference).** A tie-breaker is a silent pick with extra steps; the 141 duplicated names would still resolve to whichever row sorted first.

## Consequences

- Structural filters become answerable, and `find-symbol` answers stop depending on line numbers for identity.
- A full reindex per project is required: symbols are rebuilt from a reparse and references are re-extracted. That forces an `extraction_version` bump, so the fingerprint gate refuses queries until the pass runs, and there is no way to recompute `decl_hash` from rows written by the old extractor.
- A schema bump is unavoidable. If this record and ADR-0001 land together they share one bump (manifest version 7); if they land separately, this is the second. **No owner-approved reindex is needed** in the sense of a paid or destructive operation -- the reindex is the ordinary per-project pass the user already runs -- but the upgrade is not invisible: `find-*` refuses until it has run, which the release note records.
- Overloads now differ by `decl_hash` rather than by line, so a `find-symbol` answer for a C++ or C# overload set is stable across edits to earlier files.
- `graph.py`'s trailing-name branch stays as the fallback path, so the fan-in code is not simplified away yet; a later leg may delete it once resolved targets are populated.

## What this record does not decide

- The edit-plan schema, its validation steps and how revalidation reports structural versus semantic verification -- the successor record set owns that; it consumes the key defined here.
- Which language server, if any, supplies semantic identity, and how its identifier is stored.
- Whether `from_symbol` should become a foreign key to `symbols.id` now that an id exists. The column stays a name until a resolved target proves the join is safe.
- `changed-symbols`'s moved-versus-removed classification, which could use this identity but has its own record.
